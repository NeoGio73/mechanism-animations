## 1. What finished

**The queue stall: cause found, fixed and tested.**
- **Cause:** jobs share the 8 cores through a queue file guarded by a small "lock" file. On Windows, if one program deletes that lock file at the moment another tries to create it, the second gets "permission denied". The code expected only "file exists", so it treated the clash as an error. That error killed the waiting thread of the default-settings angle check at 23:24. Its place in the queue stayed behind, at the head. The queue is first-come-first-served, so everything waited behind a place nobody was going to use. From 23:34, no job started.
- **Proof:** on a scratch copy of the queue, the old code produced the same error 4 times in 90 s and stalled the same way.
- **Fix (`pipeline/cores.py`):**
  - The clash now means "busy, try again".
  - A waiting thread that fails removes its own place.
  - Every waiter checks in at each poll, and a place without a check-in for 2 minutes no longer blocks anyone.
- **Tests on the scratch copy:**
  - A planted dead place, like last night's: the job behind it started after the skip time; under the old code it never started.
  - 192 of 192 rapid queue cycles completed, with 0 errors and nothing left behind.
- **Live queue:** restarted on the fixed code at 06:22.
- **Second fix (06:26):** two high-priority lanes kept cutting ahead of each other, because each new priority request went to the very head. Priority requests are now first-come-first-served among themselves.

## 2. What failed and what I did

**The Hessian-every-5-steps tail test (EulerPC) failed.**
- **Why ORCA did not end normally:** pysisyphus sent it a geometry made entirely of NaN (not-a-number) coordinates.
- **The chain of events:**
  - At C–O ≈ 3.1 Å, the integrator's correction stage hit an oscillation on its own interpolated surface. It returned a step of 0.027 bohr·amu½, then a step of exactly zero.
  - The next Hessian update divided by that zero step and filled the Hessian with NaN.
  - The first tail option (EulerPC without Hessian recalculation) failed in exactly the same way yesterday.
- **Fix:** if a corrected step comes out shorter than half the step length, the predicted point (full step length) is kept, and the event is counted and reported.
- **Rerun:** in a clean folder, both sides.

**Gonzalez–Schlegel "converged" after one step. It had not converged.**
- I replayed the step offline from its recorded Hessian and gradients, and the replay reproduced the failure exactly.
- **The chain of events:**
  - The Hessian update after the first micro-step turned the lowest curvature from −0.015 to −0.62 au. This update formula (BFGS) is unstable where the curvature is negative, as in these flat tails.
  - The search for the step multiplier λ then diverged.
  - pysisyphus treats that failure as "converged". The same probably happened in the early 0.025 run.
- **Fix:**
  - the update formula used by EulerPC (Bofill);
  - translations and rotations removed from the Hessian, in the molecule's current frame;
  - a bracketed search for λ, which has exactly one root on the interval it searches;
  - a failed search now counts as a failure, never as convergence.
- **Check:** on the same recorded data, the step now converges in 2 micro-steps to a full 0.0999 step.
- **Rerun:** in clean folders, both sides.
